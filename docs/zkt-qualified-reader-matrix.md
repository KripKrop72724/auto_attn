# Exact-reader policy for the 2.7 writer

The checked-in `apps/add_backend/zk_add/zkt_reader_matrix.json` is the authoritative package policy. `BLOCKED` has no reader identities: a writer may compile for development validation, but writer admission and release tooling refuse it. `PINNED` binds both reviewed signed reader packages; it does not establish installation, rollback qualification or a HIL pass. The source activation review must retain the verified manifests, signatures, application/artifact/ELF identities and source commits used for those pins.

The two ordered structural slots are ordinary reader **2.6.23** and factory reader **2.6.22**. The earlier 2.6.21 canary reported a DMA allocation failure and has no accepted readiness evidence; its historical artifact remains auditable but cannot fill the ordinary-reader slot. Only independently verified signed 23 and 22 package identities may populate this policy through a reviewed source change; neither slot itself is a field qualification claim.

## Policy and runtime enforcement

Each populated entry must contain exactly the version, release ID, ESP application SHA256, whole signed artifact SHA256, source commit and signing key ID. Both actual signed packages must exist and be independently verified before a reviewed source change populates the matrix. No command-line policy file or environment override is accepted by the generator/signing helper. Its canonical sorted compact JSON hash binds the V5 compiled marker, signed manifest and selected-reader evidence. Missing, duplicate, unexpected or mistyped entries fail closed.

The manifest's coarse bootstrap minimum is the numerically lowest matrix version, independent of preferred reader order. For the 23/22 ordering this is 22, while exact version, package and per-device qualification checks still follow. A higher preferred version cannot silently exclude the second qualified reader through ADD's earlier semantic-version gate.

Before writer vault decryption, the signer also executes a bounded verifier inside the existing ADD container. It uses ADD's configured firmware store and public trust root, with a read-only catalog transaction; no catalog synchronization or attendance operation occurs. The deployed matrix must match the compiled writer hash. Every reader must have an exact, non-revoked HIL catalog row and matching publication metadata, canonical RSA-signed manifest, whole signed artifact hash, RSA secure-boot-v2 signature (including signed padding), application hash/descriptor, and compiled reader contract. Missing packages, old deployed policy or unsupported reader validation blocks signing. This is package verification, not device eFuse verification or field qualification.

The firmware keeps the existing 192-byte reader proof format. It checks the actual retained OTA slot, secure boot, encrypted NVS, slot validation, terminal/epoch/layout binding and the selected exact version/application digest before enabling the writer or selecting a rollback image. Its telemetry identifies the retained proof generation and slot. A RAM health snapshot cannot invent a successful proof, and the storage owner clears the reported selection when compatibility is not established. The new telemetry cache is compiled only for the V5 writer. Older readers continue rejecting proofs from newer bridge versions; the historical V4/17 contract remains readable for audit and recovery, but cannot authorize a new writer release.

ADD saves the selected complete reader entry and matrix hash in the deployment's unique committed OFFERED event. Reoffers, downloads, full HIL start, each sealed telemetry sample and final current sample must remain bound to that selection. A controlled reboot may expose an explicitly classified unfinished startup sample; only independently verified recovery permits that transition. Failed-boot receipts select the committed entry, not whichever allowed version a return message claims. Existing complete-byte, immediate-predecessor, wrong-slot and stale-attempt checks remain required.

A target must independently earn a matching stored BRIDGE_READY verdict and supply fresh current reader/preservation evidence. Factory 22 additionally requires its exact stored revoked factory-trial proof. A signed 22 package may be included in the final writer before 22's field qualification: first qualify the ordinary reader and run full 2.7 HIL on 3FL; then permit the exact three factory trials; each factory device earns its own 22 readiness before installing that same writer. Signing is not field qualification, and no 22-on-3FL pass is inferred.

Factory 22 publication uses the full 17-device signed inventory plus a separate exact three-device trial contract. Its general legacy bootstrap allowlist is empty. Publisher and expansion inputs accept only an ordered prefix of those three factory targets. Earlier bridge artifacts, scopes and original minimum versions remain unchanged.

Validation uses synthetic identities in isolated temporary files/databases only. The host proof harness preserves the on-disk format and checks old/new proof direction, selected-reader evidence, mismatches and read failures. Backend tests cover committed selection, both selected readers, replay and substituted package identities on SQLite/PostgreSQL. PowerShell tests use a disposable repository copy for populated policy examples. Explicit isolated BLOCKED and PINNED fixtures keep both refusal and acceptance coverage independent of policy activation. Actual ESP-IDF builds use the checked-in policy, with its count and hash recorded in build evidence. These tests do not supply physical endurance, power-loss, capacity or nationwide acceptance evidence.
