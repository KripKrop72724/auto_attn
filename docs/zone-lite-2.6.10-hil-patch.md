# Zone Lite 2.6.10 capacity-pressure HIL patch

On 27 September 2026, the SLICTOWER 13FL 2.6.9 deployment failed boot confirmation and returned to its signed 2.4.12 application. During the candidate boot, the ESP reported `capacity_admission` / `ENOSPC` for an optional historical ADD identity-catalog write while flash usage exceeded the historical-write threshold. No flash read or write failure was reported. The catalog remained authenticated and bounded in memory, but the reserve refusal set `last_error` and latched `LOCAL_FAILURE`, preventing queue recovery and persistence proof.

2.6.10 keeps the historical-write reserve and verified in-memory catalog fallback. A capacity-policy refusal no longer sets a queue filesystem error or a fatal LED state; actual measurement, open, write, fsync, and activation failures still do. Boot health must still prove live queue recovery and persistence. The signed storage contract adds only the immutable 2.6.9 application digest as a predecessor; its original 2.4.12, 2.5.2, and HIL predecessor checks remain exact.

The 2.6.10 package must be signed from a green `main` commit and published `HIL_ONLY` with the five exact targets in `deploy/add/hil-targets-2.6.10.json`. Swat, SLICTOWER 13FL, and SLICTOWER 3FL can run independent first-stage HIL campaigns. Peshawar remains gated by formal acceptance for all three first-stage targets, then proceeds in the signed order. No nationwide promotion follows publication or boot confirmation alone.

SLICTOWER 3FL currently runs the signed 2.4.12 application from `factory`. The 2.6.10 rollback guard requires an authenticated application in the other OTA slot. The exact live 3FL connector can first receive the already published signed 2.5.2 image from a one-device campaign. The bridge preflight and each download grant recheck connector ID, MAC, terminal serial, connectivity, factory partition, and 2.4.12 application digest; the offline spare is excluded. Confirm 2.5.2 boot and queue health before offering 2.6.10 to 3FL.

For each candidate HIL, require the signed image and application digests, completed boot confirmation, healthy storage and workers, fresh ADD telemetry, and the requested real attendance punches. Retain `HIL_ONLY` while monitoring and record any missing physical evidence as incomplete.
