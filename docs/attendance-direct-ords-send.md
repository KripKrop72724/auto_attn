# Administrator Oracle send from Attendance

The **Attendance → All events** ledger supports multi-select Oracle status and CNIC-availability filters, a selectable load size, and single or bulk **Send to ORDS**. Filters combine. The page never changes captured punch facts.

For one punch, use **Send to ORDS** in its row. For a batch, check punches in the list (or **Select loaded punches**) and choose **Send selected punches**. One batch contains at most 500 saved punches. The review dialog shows the selection and requires one reason and an administrator password. Approval creates one durable, audited run; it is not an Oracle acknowledgement.

ADD excludes a punch when its current synced terminal user is unknown or that user has no usable CNIC. It also refuses, at approval and again before dispatch, any punch whose terminal clock was `INVALID` or whose time is impossible (before 2010, or more than a day after it was captured, received or now). An approval saved earlier for such a punch is quarantined as `QUARANTINED_INVALID_DEVICE_TIME`, never sent.

If the saved punch has a usable CNIC, the approved Oracle payload uses it. Otherwise ADD reads everything it retained about who held that terminal user ID at the punch time: identity records covering the punch (including revoked ones and ones for another terminal UID), the CNIC the terminal captured with the punch, deleted identities, the terminal user the punch was linked to at ingest, the name saved with the punch and, when no record covers the punch, the record that ended just before it and the one that started just after it. The result decides what the administrator may choose:

- **Only today's CNIC** in those records, including a break between two records of today's own terminal user holding today's CNIC: today's CNIC and name are used without asking.
- **One other CNIC covering the punch** (for example a CNIC edited on the terminal after the punch), or the same other CNIC on the records just before and after the punch for the same terminal user (a break between snapshots): the dialog shows both masked CNICs and the punch-time CNIC is selected by default. Today's CNIC is offered only when the punch-time record is the same terminal user record.
- **No record covers the punch and the CNIC changed around it** (the old CNIC's record ended before the punch, today's started after it): only what is close to the punch is offered, for that punch alone and with nothing selected. The old CNIC is offered only when today's own terminal user record held it until at most 30 minutes before the punch (an in-place edit) and its holder was not deleted in between; today's CNIC only when its record started at most 30 minutes after the punch. The dialog shows when each record ended and started. A record of another terminal user that ended within 30 minutes before the punch, or nothing within 30 minutes on either side, refuses the punch (`CNIC_CONFLICT`).
- **No record, or records that do not prove today's CNIC** (revoked, another UID, another terminal user record): today's CNIC is used only after an explicit confirmation. Punches with no record share one confirmation per terminal, serial, user ID and position in ADD's history; a punch older than ADD's first record of the user ID is confirmed separately and the dialog shows that first date. Revoked or other-UID records, and a saved name that is not today's user's, are confirmed one punch at a time.
- **Another CNIC or person in the evidence that does not name one usable CNIC** (two other CNICs, a captured CNIC that differs, a holder deleted at or after the punch, a punch linked to another terminal user, or another CNIC on one side of an uncovered punch only: after ADD's last record, before its first record such as a mistyped CNIC fixed later, or today's CNIC before the punch and another after it): the punch is refused (`CNIC_CONFLICT`) and cannot be sent by hand.
- **An unresolved duplicate CNIC** (two active terminal users hold today's CNIC): the punch is refused (`IDENTITY_CONFLICT_UNRESOLVED`) until the duplicate is resolved in ADD Users. A single punch time with more identity records than ADD reads at once is refused as `PUNCH_TIME_RECORDS_TOO_MANY`; a long selection is read in parts and never refused for its size.

Every choice echoes the opaque `evidence_digest` the preview returned for that punch. If ADD's records changed before approval (a new record, signal, holder or CNIC), the punch is skipped as `CNIC_CHOICE_STALE`; reload the dialog and decide again. Sending a punch-time CNIC that another active terminal user holds today needs its own explicit confirmation (`held_by_other_confirmed`, set when the administrator selects that CNIC; there is no default); the approval records it, and a holder that appears after an approval stops an approval that did not accept it. A request that leaves a choice unmade (for example from an older dashboard) skips that punch; ADD never picks the current CNIC by user ID alone. A conflict between a saved CNIC and the current user does not itself prevent this explicit override.

Punches that ADD's own identity proof (and the installed database guard) would release at the next user snapshot, or that arrived after the latest snapshot and are re-checked at the next one, are listed separately. They are skipped unless the administrator ticks **Send now anyway**; the decision records that override. The dialog loads these read-only checks from `POST /api/v2/attendance-direct-ords/preview` before approval is possible. The slow automatic-release checks run before ADD takes the scheduler lock; under the lock every row is read again from the database and every identity, time, choice and delivery check runs again. A LIVE punch counts as awaiting the next snapshot only when that snapshot's own proof can still release it (the roster unchanged since the punch, the saved name today's name, captured within 10 minutes of the punch).

An approved punch is checked again when it is queued and before every delivery. It stops when a new record, holder or CNIC appears that the administrator did not see, when today's CNIC changes under a send that uses it, or when the punch time is invalid. A stopped approval is handled in one of three ways:

- If ADD's own identity proof later releases the punch, ordinary delivery takes it over; the stopped approval's item closes as `AUTO_RELEASED` once Oracle confirms. Ordinary delivery treats Oracle's "already stored" reply as success without a content check, so this takeover happens only when nothing under the approval can be in Oracle with another CNIC: the approval never POSTed, or what it POSTed carries the same CNIC (its item is then still marked for attention).
- If it may already have POSTed another CNIC (a reply was lost or the content check failed) and ADD's proof then releases the punch, the punch is held as `QUARANTINED_IDENTITY_CONFLICT` with `PREVIOUS_POST_UNCERTAIN`; the snapshot release does not touch it again. Review the Oracle record first.
- If it never POSTed to Oracle, an administrator may replace it with a new explicit approval (the dialog says so); the old item closes as `SUPERSEDED`. This includes an approval that stopped while ADD holds the punch and whose evidence later validates again: nothing would resume it otherwise. An approval held by a duplicate CNIC that is later resolved as the same employee (a CNIC saved with the punch, today's CNIC or a punch-time CNIC) resumes at the next complete snapshot after the same full re-check.
- If it may already have POSTed (a reply was lost), it cannot be replaced (`PREVIOUS_POST_UNCERTAIN`) and stays for review, because Oracle may already hold the earlier identity for that event UID.

For a single held punch, `GET /api/v2/attendance/{event_id}/identity-evidence` explains the same facts: the read-only database-guard result, the punch-time and current CNIC (masked), the record position, first-observed date and the edge times of the records around an uncovered punch, whether a saved terminal record exists yet, and whether an automatic release is expected at the next snapshot. Already Oracle-confirmed punches and punches owned by another delivery are also accounted for without duplicate submission. For the other selected punches, this action overrides ADD's normal delivery holds but preserves the original event UID, time, punch facts and raw evidence. It records the administrator's explicit decision; using the current user does not create historical identity proof or change Oracle data already present.

Hikvision terminals follow the same rules: their ISAPI profile scans record the same identity history once both scans match. A Hikvision punch held before ADD knew the employee profile is older than ADD's first record and needs an explicit confirmation.

The saved run shows preparing, waiting, confirmed, skipped and attention-needed counts. The run link survives a browser or server restart. A **Forced** pill appears only after a per-punch decision is committed; it opens the administrator reason and audit reference. `ACKED_CHECK` appears only after Oracle's protected content check confirms matching identity and source facts. A successful HTTP response alone is not completion. Rejections and mismatches remain visible for review. If a reply is lost, ADD verifies before retrying; it records send intent first so an uncertain response cannot trigger an uncontrolled repeat.

The existing **Needs review → Force release attendance** workflow remains separate: it checks a fresh terminal user list before approving historical identity use. This All events action is an explicit, broader delivery override for individually selected saved punches.

## Terminal names with a CNIC typo

A terminal name such as `A.Saleem-A4230111028815` (a letter before the 13 digits) or `Ali Khan-42301-1102881-5` (dashes) does not give ADD a CNIC, so every punch by that user stays held. ADD Users marks such a user, the integrity summary counts them, and the terminal raises a `USER_CNIC_FORMAT_SUSPECT` alert (user IDs only). ADD never uses the suspect digits. Confirm the CNIC with HR, then set it in **ADD Users → Edit**: the dialog proposes the name without the suffix, and the server strips it too, so the 24-byte terminal name becomes `A.Saleem-<CNIC>` rather than `A.Saleem-A-<CNIC>`. A `-S` shift-worker marker inside the unparsed suffix is kept as the shift-worker flag. The alert clears at the next user snapshot. Punches held before the CNIC was set are older than ADD's first identity record for that user and still need an explicit confirmation of today's CNIC.
